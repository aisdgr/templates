# AIGDMM
## AI 治理文件驅動開發方法論 (AI-Governed Document-Driven Methodology)

**版本：** 1.2  
**狀態：** 標準規範 (Normative Specification)

---

## 0. 標準優先級 (Normative Precedence)

本文件為 AIGDMM 的**權威標準規範**。

本文件中定義的所有文件類別、治理規則、約束 (Constraints)、追蹤機制 (Trace Mechanisms) 及優先順序關係均具備**約束力**。

任何概念性、解釋性或說明性文件（包括 *AIGDMM_Conceptual_Model.md*）均僅供**參考 (Informative only)**。

> 若有任何不一致之處，**應以本文件為準**。

---

## 1. 目的

AIGDMM 定義了一套用於 AI 輔助軟體開發與執行的文件驅動治理方法論。

其目的在於：

- 明確定義文件的權限與責任。
- 透過明確的治理約束來限制 AI 行為。
- 分離語義 (Semantics)、工程、治理、執行與證據。
- 實現可審計性、不可否認性以及受控的演進。
- 防止不受控的 AI 驅動偏差 (AI-driven drift)。

AIGDMM 將文件視為**治理原語 (Governance Primitives)**，而非 AI 生成的產物或瞬態上下文 (Transient contexts)。

---

## 2. 核心治理原則

### 2.1 人類權威 (Human Authority)

所有**標準文件 (Normative Documents)** 均由人類擁有。

AI 可以根據治理約束閱讀文件，但除非獲得明確許可，否則**不得**生成、修改或擴展標準文件。

---

### 2.2 基於類別的治理 (Class-Based Governance)

所有文件均依據其**治理角色**進行分類，而非依據格式、工具或儲存媒介。

文件類別決定了：

- 權限歸屬
- 可變性 (Mutability)
- 生命週期
- AI 權限
- 證據權重

---

### 2.3 邊界強制執行 (Boundary Enforcement)

每種文件類別均擁有**排他性責任**。

禁止跨類別的責任滲漏。

若資訊屬於另一類別，**必須**透過「追蹤 (TRACE)」進行引用，不得重複定義或重新定義。

---

## 3. 文件類別分類學 (Document Class Taxonomy)

---

### 3.1 S-類 — 語義 / 規格 (Semantic / Specification)

**目的：** 定義**系統是什麼 (What)**。

| 文件    | 描述                                                 |
| :------ | :--------------------------------------------------- |
| **SRS** | 軟體需求規格書 (Software Requirements Specification) |
| **SDS** | 軟體設計規格書 (Software Design Specification)       |
| **STS** | 軟體測試規格書 (Software Test Specification)         |

**治理規則：**

- 人類擁有。
- 內容固定。
- **不得**應用元模型 (Meta-Model) 轉換。
- AI **不得**生成、修改或擴展。

**備註：**

- 所有語義、行為與含義**必須**存在於 S-類文件中。
- 其他類別僅能透過 TRACE 引用 S-類文件。

---

### 3.2 C-類 — 工程 / 實作規格 (Engineering / Implementation Specification)

**目的：** 定義**系統被允許如何進行工程開發 (How)**。

C-類文件指定：

- 架構約束 (Architectural Constraints)。
- 結構邊界。
- 工程不變量 (Engineering Invariants)。
- 實作慣例。

C-類文件**不得**定義：

- 業務行為。
- 語義含義。
- 控制流。
- 運行時邏輯。

| 文件    | 描述                                               |
| :------ | :------------------------------------------------- |
| **CAS** | 代碼架構規格書 (Coding Architecture Specification) |
| **CIS** | 概念實作規格書 (Conceptual Implementation Spec)    |
| **CSS** | 代碼結構規格書 (Coding Structure Specification)    |

**治理規則：**

- 人類擁有。
- 內容固定。
- **不得**應用元模型轉換。
- AI **不得**生成或修改。

---

### 3.3 G-類 — 治理 / AI 約束 (Governance / AI Constraints)

**目的：** 定義在生成與執行期間規範 AI 行為的**憲法規則與硬約束**。

G-類文件指定：

- AI 被**禁止或允許**執行的行為。
- 執行與生成的邊界。
- 防止 AI 偏差的不可逾越約束。

G-類文件**不得**定義：

- 系統架構。
- 工程結構。
- 業務語義。
- 功能需求。

#### G-類文件類型

| 文件    | 描述                                             |
| :------ | :----------------------------------------------- |
| **GCG** | 治理憲章指南 (Governance Constitution Guide)     |
| **GCS** | 治理代碼標準 (Governance Coding Standard)        |
| **GEC** | 治理執行約束 (Governance Execution Constraints)  |
| **GGC** | 治理生成約束 (Governance Generation Constraints) |

**治理規則：**

- G-類文件由**人類擁有**。
- G-類文件可以是：具備版本的、具備時效性的、受授權限制的、或可撤銷/過期的。
- AI **必須**在運行時強制執行 G-類約束。
- 違反任何 G-類約束**必須**：被偵測、被記錄，並導致執行失敗或阻斷。

**優先級規則：**

G-類約束優先於：

- AI 生成行為。
- 任何非標準指令。

G-類約束**不會**覆蓋：

- S-類的語義權威。
- C-類的工程約束。

---

### 3.4 E-類 — 執行規格 (Execution Specification)

**目的：** 定義**經授權、可審計的執行行為**。

E-類文件指定：

- 允許哪些執行行為。
- 在何種邊界與來源權威下進行。
- 如何判定成功與失敗。
- 執行流程如何演進。

E-類文件定義執行規則，**不**記錄執行結果。

#### E-類文件類型

| 文件    | 描述                                          |
| :------ | :-------------------------------------------- |
| **VEP** | 版本執行計劃 (Version Execution Plan)         |
| **PEP** | 流水線執行計劃 (Pipeline Execution Plan)      |
| **TES** | 任務執行規格書 (Task Execution Specification) |

**治理規則：**

- E-類文件由**人類編寫**。
- E-類文件具有**標準性 (Normative)**。
- AI **可以**閱讀 E-類文件。
- AI **不得**生成、修改或擴展 E-類文件。
- 執行行為**必須**嚴格符合 E-類定義。
- 執行行為**必須**引用衍生自 E-類文件的有效**追蹤錨點 (Trace Anchors)**。

**執行權威層級：**

- **VEP** 定義「版本級」執行權限。
- **PEP** 定義「流水線級」執行權限。
- **TES** 定義「任務級」執行權限。

低層級的執行**不得**違反高層級定義的約束。

**強制記錄規則：**

每一項受 E-類文件治理的執行行為，**必須產生一個對應的執行記錄 (Execution Record, ER)**。

無執行記錄 (ER) 的執行被視為**無效 (INVALID)**。

---

### 3.5 R-類 — 報告 / 證據 (Report / Evidence)

**目的：** 證明**已經發生了什麼**。

R-類文件是 AIGDMM 唯一認可的**證據產物 (Evidential artifacts)**。

#### 執行記錄 (Execution Record, ER)

執行記錄將「執行結果」與其對應的「E-類治理文件」綁定。

| 記錄    | 描述                                       |
| :------ | :----------------------------------------- |
| **VER** | 版本執行記錄 (Version Execution Record)    |
| **PER** | 流水線執行記錄 (Pipeline Execution Record) |
| **TER** | 任務執行記錄 (Task Execution Record)       |

**治理規則：**

- R-類文件由**系統自動生成**。
- R-類文件是**不可變的 (Immutable)**。
- R-類文件**不得**由人類或 AI 修改。
- 每個 ER **必須**引用：
  - 其治理 E-類文件。
  - 其追蹤錨點 (Trace Anchor)。
  - 執行時間戳記。
  - 執行結果。
  - 產出的產物清單。

**層級規則：**

執行記錄**必須**形成層級鏈：

```
TER → PER → VER
```

---

## 4. 追蹤 (Trace) 與 追蹤錨點 (Trace Anchor)

### 4.1 追蹤錨點 (Trace Anchor)

**追蹤錨點**是一個穩定、不可變的治理參考，用以綁定**權威、執行與證據**。

追蹤錨點：

- 唯一識別一個治理文件實例。
- 將執行錨定到特定的版本與狀態。
- 實現可審計性與不可否認性。

**追蹤錨點屬性：**

每個追蹤錨點**必須**包含：

- 錨點 ID (全球唯一)
- 文件類別與類型
- 文件識別碼
- 文件版本
- 哈希 (Hash) 或簽章（選填，但建議使用）
- 有效範疇（時間 / 授權 / 環境）

**規則：**

- 追蹤錨點一旦發布即**必須**不可變。
- 執行過程**必須**引用追蹤錨點，而非原始文件。
- 若治理文件過期或被撤銷，其追蹤錨點對於未來的執行即變為無效。

---

### 4.2 TRACE 規則

TRACE 是文件之間的**鏈結機制**。

TRACE 的作用：

- 將規格連結至實作。
- 將執行規格 (E-Class) 連結至執行記錄 (ER)。
- 實現完整的審計重建。

TRACE **不得**：

- 重複內容。
- 重新定義權威。
- 繞過治理約束。

---

## 5. 變更與重構治理

- 所有語義變更**必須**反映在 S-類文件中。
- 所有結構變更**必須**反映在 C-類文件中。
- G-類的變更僅影響**未來的執行**。
- R-類文件**不得**觸發結構或語義變更。

---

## 6. 總結

AIGDMM 建立了一個嚴格的、基於類別的治理模型，其中：

- 含義是明確的。
- 工程是受約束的。
- AI 行為是受治理的。
- 執行是經指定的。
- 證據是不可變的。
- 責任是可追蹤的。

**文件類別決定權限。** **執行受 E-類治理。** **證據由 ER 記錄。** **追蹤錨點決定責任歸屬。**
