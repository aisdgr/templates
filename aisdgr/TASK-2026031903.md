## 評估 1: 共用規則獨立分類的可行性

### 1.1 當前問題分析

**現狀**: CODE 和 DOCS Domain 存在相似或相同的規則

**範例對比**:

| 行為限制類型  | CODE 規則                          | DOCS 規則                            | 相似度 |
| ------------- | ---------------------------------- | ------------------------------------ | ------ |
| AR - 製品隔離 | CODE-AR-C-01: 禁止創建未聲明的製品 | DOCS-AR-C-01: 僅在聲明的佔位符內生成 | 高     |
| BD - 邊界控制 | CODE-BD-C-01: 不得修改邊界外程式碼 | DOCS-BD-C-01: 批准後文檔必須不可變   | 中     |
| TR - 可追溯性 | CODE-TR-P-01: 代碼必須包含追溯 ID  | DOCS-TR-P-01: 應使用認可的語義源     | 中     |

**問題**:
- 相似規則重複定義
- 維護成本高（修改一處需同步多處）
- 違反 DRY (Don't Repeat Yourself) 原則

---

### 1.2 Concept.md 的相關原則

**Category Ruleset 的互斥性** (Concept.md 第 120-125 行):
```
∀ C₁ ≠ C₂ ∈ Behavior_Category:
  Category_Ruleset(C₁) ∩ Category_Ruleset(C₂) = ∅
```
> 即：不同 Behavior Category 的 Category Ruleset 互不重疊（互斥分區）

**Rule 與 Application Ruleset 的多對多關係** (Concept.md 第 89-101 行):
```
Rule : Application_Ruleset = N : N

∀ rule ∈ Library:
  ∃ {P₁, P₂, ..., Pₖ} ⊆ Principle:
    rule ∈ Application_Ruleset(Pᵢ), ∀ᵢ
```
> 即：一條 Rule 可被組合進多個 Application Ruleset

**關鍵發現**:
- **Category Ruleset 必須互斥**：一條 Rule 只能屬於一個 Category
- **Application Ruleset 可以重用**：一條 Rule 可以被多個 Application Ruleset 引用

---

### 1.3 共用規則獨立分類的方案

#### 方案 A: 建立「通用 Domain」（CORE/COMM/GEN）

**架構**:
```
CORE Domain (通用規則)
├── AR - Artifact Isolation
│   ├── CORE-AR-C-01: 禁止創建未聲明的製品類型
│   └── CORE-AR-P-01: 創建新製品的權限必須明確定義
├── BD - Boundary & Stop
├── TR - Traceability
│   ├── CORE-TR-P-01: 生成的製品必須包含追溯 ID
│   └── CORE-TR-P-02: 追溯 ID 必須嵌入在製品本身中
└── ...

CODE Domain (程式碼特定規則)
├── ST - Structural Change (僅程式碼適用)
├── TI - Test Integrity (僅程式碼適用)
└── ...

DOCS Domain (文檔特定規則)
├── ST - Structural Change (僅文檔適用)
└── ...
```

**Application Ruleset 組合**:
```
Application_Ruleset("Code Generation") = {
  CORE-AR-*,      // 引用通用規則
  CORE-BD-*,
  CORE-TR-*,
  CODE-ST-*,      // 程式碼特定規則
  CODE-TI-*
}

Application_Ruleset("Documentation Generation") = {
  CORE-AR-*,      // 引用相同的通用規則
  CORE-BD-*,
  CORE-TR-*,
  DOCS-ST-*       // 文檔特定規則
}
```

**優點**:
- ✅ 消除重複定義
- ✅ 維護成本低（修改一處生效多處）
- ✅ 符合 DRY 原則
- ✅ 符合 Concept.md 的 Application Ruleset 機制

**缺點**:
- ⚠️ 增加 Domain 數量
- ⚠️ 需要明確區分「通用」vs「特定」的邊界
- ⚠️ Rule ID 結構需調整

**與 Concept.md 的一致性**:
- ✅ Category Ruleset 互斥：CORE/CODE/DOCS 各自的 Category 不重疊
- ✅ Application Ruleset 重用：Code/Doc Generation 都引用 CORE 規則
- ✅ Rule Library = ⋃ Category_Ruleset(C)

---

#### 方案 B: 保持現狀，透過 Application Ruleset 組合

**架構**:
```
CODE Domain (完整規則集)
├── AR - Artifact Isolation (程式碼版本)
├── BD - Boundary & Stop (程式碼版本)
└── ...

DOCS Domain (完整規則集)
├── AR - Artifact Isolation (文檔版本)
├── BD - Boundary & Stop (文檔版本)
└── ...

Application_Ruleset("Code Generation") = { CODE-* }
Application_Ruleset("Documentation Generation") = { DOCS-* }
```

**優點**:
- ✅ 結構簡單
- ✅ 各 Domain 完全獨立

**缺點**:
- ❌ 規則重複定義
- ❌ 維護成本高
- ❌ 違反 DRY 原則

---

### 1.4 可行性結論

**建議**: 採用 **方案 A - 建立通用 Domain**

**理由**:
1. 符合 Concept.md 的 Application Ruleset 設計理念
2. 解決規則重複問題
3. 提高可維護性
4. Category Ruleset 仍然互斥，符合 Concept.md 要求

**關鍵成功因素**:
- 明確定義「通用」vs「特定」的判斷標準
- 建立清楚的 Rule ID 命名規則
- 文檔化 Application Ruleset 的組合邏輯

## 評估 2: 新分類的命名建議

### 2.1 命名選項分析

| 候選名稱 | 全稱             | 優點                 | 缺點                      | 推薦度 |
| -------- | ---------------- | -------------------- | ------------------------- | ------ |
| CORE     | Core Rules       | 簡潔、語義明確       | 可能與「核心業務」混淆    | ⭐⭐⭐⭐   |
| COMM     | Common Rules     | 語義直觀             | 縮寫不明顯                | ⭐⭐⭐    |
| GEN      | General Rules    | 語義通用             | 過於泛化，不夠具體        | ⭐⭐     |
| BASE     | Base Rules       | 強調基礎性           | 可能被誤解為「底���技術」 | ⭐⭐⭐    |
| SHARED   | Shared Rules     | 語義精確             | 名稱較長                  | ⭐⭐⭐    |
| META     | Meta Rules       | 符合「元規則」概念   | 可能與「元數據」混淆      | ⭐⭐     |
| GOV      | Governance Rules | **已存在**，治理專用 | 不適合（語義不同）        | ❌      |

---

### 2.2 推薦命名方案

#### 主推薦: **CORE**

**理由**:
1. **語義清晰**: Core 表示「核心、基礎」，符合通用規則的定位
2. **簡潔**: 4 個字母，易於記憶和輸入
3. **對稱性**: 與 CODE、DOCS 形成良好的對稱結構
4. **行業慣例**: Core 在軟體架構中常用於表示基礎層（如 Core Module、Core Library）

**使用範例**:
```
CORE-AR-C-01: Must not create undeclared artifact types
CORE-BD-C-01: Must not operate beyond declared boundaries
CORE-TR-P-01: Generated artifacts must include traceability IDs
```

---

#### 替代推薦: **COMM** (Common)

**理由**:
1. **語義直觀**: Common 直接表達「共用、通用」的含義
2. **與 Application Ruleset 概念對應**: Common Rules 可被多個 Application Ruleset 共用

**使用範例**:
```
COMM-AR-C-01: Must not create undeclared artifact types
COMM-BD-C-01: Must not operate beyond declared boundaries
```

---

### 2.3 最終建議

**推薦**: **CORE**

**完整架構**:
```
Domain 層級:
├── CORE   - 通用規則（跨域共用）
├── CODE   - 程式碼特定規則
├── DOCS   - 文檔特定規則
├── LANG   - 語言特定規則
└── GOV    - 治理規則（維持現狀）
```

## 評估 3: Rule ID 命名規則重新定義

### 3.1 當前 Rule ID 格式問題

**當前格式**: `{DOMAIN}-{SUBCATEGORY}-{TYPE}-{NUMBER}`

**問題**:
1. **SUBCATEGORY 語義不一致**:
   - CODE/DOCS 使用 AR、BD、CN 等限制類型
   - LANG 使用 GO、JAVA、JS 等語言名稱
   - GOV 使用 ENF、PR 等治理分類

2. **NUMBER 缺乏語義**:
   - 純數字序號（01、02、03）
   - 無法從 ID 看出規則的具體內容或層級

3. **缺乏擴展性**:
   - 難以支援子類型或變體
   - 難以表達規則之間的關聯

---

### 3.2 新的 Rule ID 命名規則設計

#### 設計原則

1. **一致性**: 所有 Domain 使用相同的結構邏輯
2. **可讀性**: 從 ID 能推斷規則的大致內容
3. **可擴展性**: 支援子類型、變體、關聯
4. **簡潔性**: 避免過長的 ID

---

#### 提議的新格式

**格式**: `{DOMAIN}-{CATEGORY}-{SUBTYPE}-{NUMBER}`

**組成部分**:

1. **DOMAIN** (2-4 字母): 領域代碼
   - `CORE`: 通用規則
   - `CODE`: 程式碼規則
   - `DOCS`: 文檔規則
   - `LANG`: 語言規則
   - `GOV`: 治理規則

2. **CATEGORY** (2 字母): 行為限制類型
   - `AR`: Artifact Isolation
   - `BD`: Boundary & Stop
   - `CN`: Constraint Neutrality
   - `LG`: Logging & Report
   - `ST`: Structural Change
   - `TI`: Test Integrity
   - `TR`: Traceability
   - `ENF`: Enforcement (GOV 專用)
   - `PR`: Principles (GOV 專用)

3. **SUBTYPE** (可選，0-3 字母): 子類型或特定範疇
   - `C`: Constraint (MUST NOT)
   - `P`: Policy (MUST)
   - `GO`: Go 語言
   - `JV`: Java 語言
   - `JS`: JavaScript
   - `PY`: Python
   - `RS`: Rust
   - `TS`: TypeScript
   - `STD`: 標準/通用

4. **NUMBER** (3 位數字): 序號
   - 001-999
   - 可預留號段（如 001-099 為核心規則，100-199 為擴展規則）

---

#### 使用範例

**通用規則 (CORE)**:
```
CORE-AR-C-001  (通用製品隔離約束)
CORE-BD-P-001  (通用邊界控制政策)
CORE-TR-P-001  (通用可追溯性政策)
```

**程式碼規則 (CODE)**:
```
CODE-ST-C-001  (程式碼結構變更約束)
CODE-TI-C-001  (測試完整性約束)
```

**語言規則 (LANG)**:
```
LANG-ST-GO-001 (Go 語言結構約束)
LANG-ST-JV-001 (Java 語言結構約束)
LANG-ST-JS-001 (JavaScript 語言結構約束)
```

**治理規則 (GOV)**:
```
GOV-ENF-C-001  (執行機制約束)
GOV-PR-C-001   (治理原則約束)
```

---

#### 與當前格式的對比

| 當前 ID      | 新 ID          | 改進點                          |
| ------------ | -------------- | ------------------------------- |
| CODE-AR-C-01 | CORE-AR-C-001  | 移至 CORE，使用 3 位數字        |
| LANG-GO-C-01 | LANG-ST-GO-001 | 增加 ST (結構) 類型，語義更清晰 |
| GOV-ENF-C-01 | GOV-ENF-C-001  | 使用 3 位數字                   |
| DOCS-ST-C-21 | DOCS-ST-C-021  | 使用 3 位數字                   |

---

### 3.3 進階命名規則（可選）

#### 分組編號規則

**格式**: `{DOMAIN}-{CATEGORY}-{SUBTYPE}-{GROUP}-{NUMBER}`

**範例**:
```
LANG-ST-GO-01-001 (Go 語言 - 結構 - 第 1 組 (錯誤處理) - 第 1 條)
LANG-ST-GO-01-002 (Go 語言 - 結構 - 第 1 組 (錯誤處理) - 第 2 條)
LANG-ST-GO-02-001 (Go 語言 - 結構 - 第 2 組 (並發控制) - 第 1 條)
```

**優點**:
- 支援邏輯分組
- 易於管理相關規則

**缺點**:
- ID 較長
- 可能過度設計

---

### 3.4 最終建議

**推薦格式**: `{DOMAIN}-{CATEGORY}-{SUBTYPE}-{NUMBER}`

**標準範例**:
```
CORE-AR-C-001
CODE-ST-C-001
LANG-ST-GO-001
GOV-ENF-C-001
```

**編號規範**:
- 使用 3 位數字（001-999）
- 001-099: 核心規則
- 100-199: 擴展規則
- 200-299: 特定場景規則

## 評估 4: LANG 作為特殊產出物行為分類的評估

### 4.1 當前理解

**用戶提問**:
> 評估將 LANG 視為應用在特殊產出物的行為分類，當成類似金融產業的產業產出物的行為需求，是否符合 Concept.md

**理解**:
- LANG 不是「語言的集合」，而是「針對特定產出物類型的行為分類」
- 類似於「金融產業」有其特殊的產出物需求（如合規報告、風險評估）
- 「程式語言」也有其特殊的產出物需求（如類型安全、記憶體管理）

---

### 4.2 Concept.md 的相關定義

**Behavior Category 的定義** (Concept.md 第 237-260 行):
```
Behavior Category 為 AI 決策行為的分類機制，
先界定決策行為類別，再從該類別衍生對應規則。

關鍵特性:
- 以 AI Decision Behavior 為分類核心（非 Domain Application）
- 一個 Behavior Category 對應一個 Category Ruleset
```

**範例 Behavior Category** (Concept.md 第 247-252 行):
```
- Code Generation Behavior
- Test Generation Behavior
- Specification Generation Behavior
- File Modification Behavior
```

**Application Ruleset 的定義** (Concept.md 第 338-377 行):
```
Application Ruleset 為基於任意應用原則所設計的規則集合體，
可為 Workflow-based、Domain-based、Risk-based、Compliance-based
或任何產業/企業自訂原則。

基數關係：Rule : Application_Ruleset = N:N
```

---

### 4.3 LANG 作為「產出物類型分類」的評估

#### 方案 A: LANG 作為 Domain（當前理解）

**定位**:
```
LANG Domain
├── Go 語言產出物行為規則
├── Java 語言產出物行為規則
├── Python 語言產出物行為規則
└── ...
```

**對應概念**:
- 類似「金融產業 Domain」有特殊的產出物規則
- 「程式語言」也是一種「產出物類型」

**符合性評估**:

| Concept.md 原則            | 符合度 | 說明                                      |
| -------------------------- | ------ | ----------------------------------------- |
| Behavior Category 定義     | ⚠️      | LANG 更像是「產出物類型」而非「決策行為」 |
| Category Ruleset 互斥性    | ✅      | 不同語言的規則互斥                        |
| Application Ruleset 靈活性 | ✅      | 可組合多個 LANG 規則                      |

**問題**:
- ❌ 語言（Go、Java）不是「Decision Behavior」
- ❌ 違反 Concept.md 第 242 行：*以 AI Decision Behavior 為分類核心*

---

#### 方案 B: LANG 作為 Application Ruleset 的組合原則

**定位**:
```
Application_Ruleset("Go Language Code Generation") = {
  CODE-ST-GO-001,  // Go 語言結構約束
  CODE-ST-GO-002,
  CODE-TI-GO-001,  // Go 語言測試約束
  ...
}

Application_Ruleset("Java Language Code Generation") = {
  CODE-ST-JV-001,  // Java 語言結構約束
  CODE-ST-JV-002,
  ...
}
```

**符合性評估**:

| Concept.md 原則            | 符合度 | 說明                                          |
| -------------------------- | ------ | --------------------------------------------- |
| Behavior Category 定義     | ✅      | 規則仍屬於 CODE Domain 的 ST、TI 等限制類型   |
| Application Ruleset 靈活性 | ✅      | 語言作為「組合原則」，符合 N:N 關係           |
| Domain-based 組合          | ✅      | 符合 Concept.md 第 353 行的 Domain-based 原則 |

**優點**:
- ✅ 完全符合 Concept.md 的架構
- ✅ 語言作為 Application Ruleset 的組合維度
- ✅ 規則仍保持對行為的限制分類（ST、TI 等）

---

#### 方案 C: LANG 作為產業/領域維度

**定位**:
```
類似於：
- FINANCE Domain (金融產業特定規則)
- HEALTHCARE Domain (醫療產業特定規則)
- LANG Domain (程式語言領域特定規則)

LANG Domain
├── AR - Artifact Isolation (語言版本的製品隔離)
├── BD - Boundary & Stop (語言版本的邊界控制)
├── ST - Structural Change (語言版本的結構約束)
└── ...
```

**符合性評估**:

| Concept.md 原則        | 符合度 | 說明                                      |
| ---------------------- | ------ | ----------------------------------------- |
| Behavior Category 定義 | ✅      | LANG 下的 AR、BD、ST 仍是「對行為的限制」 |
| Domain-based 組合      | ✅      | 符合 Domain-based Application Ruleset     |

**優點**:
- ✅ 與 CODE、DOCS 結構一致
- ✅ 語言作為「應用領域」而非「決策行為」
- ✅ 可擴展（未來可加入 FINANCE、HEALTHCARE 等）

---

### 4.4 最終評估結論

**建議**: 採用 **方案 C - LANG 作為 Domain**

**理由**:

1. **符合 Concept.md**:
   - LANG 下的 AR、BD、ST 等仍是「對行為的限制分類」
   - 符合 Behavior Constraint Category 的定義
   - 語言作為「應用領域」維度，而非「決策行為」

2. **與產業類比一致**:
   - 金融產業有其特殊的產出物需求 → FINANCE Domain
   - 程式語言有其特殊的產出物需求 → LANG Domain
   - 邏輯一致，易於理解

3. **架構對稱性**:
   - CODE Domain: 程式碼通用規則
   - LANG Domain: 語言特定規則（語言作為一種「產出物類型」）
   - 結構一致

4. **可擴展性**:
   - 未來可加入其他領域 Domain（FINANCE、HEALTHCARE 等）
   - 統一的架構模式

**關鍵修正**:
- LANG Domain 應使用標準的 AR-BD-CN-LG-ST-TI-TR 結構
- 語言特定性透過 Rule Metadata 的 `languages` 欄位表達
- 或透過 Rule ID 的 SUBTYPE 欄位表達（如 LANG-ST-GO-001）

```
AISDGR Rule Library
│
├── CORE Domain (通用規則)

│   ├── CN - Constraint Neutrality
│   ├── LG - Logging & Report

│   ├── TI - Test Integrity
│   └── TR - Traceability

│   ├── BD - Boundary & Stop (程式碼特定)
│   ├── CN - Constraint Neutrality (程式碼特定)
│   ├── LG - Logging & Report (程式碼特定)
│   ├── ST - Structural Change (程式碼特定)
│   ├── TI - Test Integrity (程式碼專用)
│   └── TR - Traceability (程式碼特定)
│
├── DOCS Domain (文檔特定規則)
│   ├── AR - Artifact Isolation (文檔特定)
│   ├── BD - Boundary & Stop (文檔特定)

│   ├── LG - Logging & Report (文檔特定)
│   ├── ST - Structural Change (文檔特定)
│   ├── TI - Test Integrity (文檔專用)
│   └── TR - Traceability (文檔特定)
│
├── LANG Domain (語言特定規則)
│   ├── AR - Artifact Isolation (語言通用)
│   ├── BD - Boundary & Stop (語言通用)
│   ├── CN - Constraint Neutrality (語言通用)
│   ├── LG - Logging & Report (語言通用)
│   ├── ST - Structural Change (語言特定，如 Go/Java/Python)

    └── PR - Principles (治理原則)
```

### Rule ID 範例

**通用規則 (CORE)**:
```
CORE-AR-C-001: Must not create undeclared artifact types
CORE-BD-P-001: Permission to create new artifacts must be explicitly defined
CORE-TR-P-001: Generated artifacts must include traceability IDs
```

**程式碼規則 (CODE)**:
```
CODE-ST-C-001: Unauthorized structural refactoring is prohibited
CODE-TI-C-001: Test artifacts must never modify production code
```

**語言規則 (LANG)**:
```
LANG-ST-GO-001: Go code must handle all errors explicitly
LANG-ST-JV-001: Java code must use explicit and appropriate types
LANG-ST-JS-001: JavaScript variables must use explicit scope
```

**文檔規則 (DOCS)**:
```
DOCS-ST-C-001: General description must describe system context
DOCS-LG-P-001: Each documentation generation must generate execution logs
```

**治理規則 (GOV)**:
```
GOV-ENF-C-001: All AI-generated code must comply with coding standards
GOV-PR-C-001: AI is a constrained executor, not an autonomous designer
```

### Application Ruleset 組合範例

```yaml
# Go 語言程式碼生成
Application_Ruleset("Go Code Generation"):
  includes:
    - CORE-AR-*        # 通用製品隔離
    - CORE-BD-*        # 通用邊界控制
    - CORE-TR-*        # 通用可追溯性
    - CODE-ST-*        # 程式碼結構約束
    - CODE-TI-*        # 測試完整性
    - LANG-ST-GO-*     # Go 語言特定約束
    - GOV-ENF-*        # 治理執行機制

# Python 語言程式碼生成
Application_Ruleset("Python Code Generation"):
  includes:
    - CORE-AR-*        # 相同的通用規則
    - CORE-BD-*
    - CORE-TR-*
    - CODE-ST-*        # 相同的程式碼結構約束
    - CODE-TI-*
    - LANG-ST-PY-*     # Python 語言特定約束
    - GOV-ENF-*
```
