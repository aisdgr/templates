## 問題重新定義

### 前次評估的錯誤

**TASK-2026031901 的錯誤理解**:
- 誤將 Behavior Category 理解為「AI 行為的分類」（如 Code Generation、Test Generation）
- 建議將 AR、BD、CN 等改為 Rule Metadata 標籤

### 正確的理解

**Behavior Category 的真正含義**:
- **不是**對 AI 行為本身的分類（做什麼）
- **而是**對 AI 行為的限制方式的分類（如何限制）
- AR、BD、CN、LG、ST、TI、TR 本身就是 Behavior Category
- 這些是在分類「對 AI 行為的限制類型」

## 需要修正的具體問題

### 問題 1: LANG Domain 結構不一致

**當前問題**:
- LANG Domain 使用語言名稱（GO、JAVA、JS）作為子分類
- 這與 CODE、DOCS 的 AR、BD、CN 結構不一致
- 語言名稱不是「對行為的限制分類」

**修正建議方案 A**: 完全對齊結構

```
LANG Domain
├── AR - Artifact Isolation
│   ├── LANG-AR-C-01 (通用語言製品隔離約束)
│   └── ...
├── BD - Boundary & Stop
│   ├── LANG-BD-C-01 (語言邊界約束)
│   └── ...
├── CN - Constraint Neutrality
├── LG - Logging & Report
├── ST - Structural Change
│   ├── LANG-ST-C-01 (通用語言結構約束)
│   ├── LANG-ST-C-02 (Go 特定結構約束)
│   ├── LANG-ST-C-03 (Java 特定結構約束)
│   └── ...
├── TI - Test Integrity
└── TR - Traceability
```

**優點**:
- 結構與 CODE、DOCS 完全一致
- 符合 Behavior Constraint Category 的定義

**缺點**:
- 需要重新組織所有語言規則
- 語言特定規則可能分散在不同 Constraint Category 中

---

**���正建議方案 B**: 語言作為 Rule Metadata

```
LANG Domain
├── AR - Artifact Isolation
├── BD - Boundary & Stop
├── CN - Constraint Neutrality
├── LG - Logging & Report
├── ST - Structural Change
├── TI - Test Integrity
└── TR - Traceability

每條 Rule 附帶 Metadata:
Rule:
  id: LANG-ST-C-01
  type: Constraint
  description: Go code must handle all errors explicitly
  metadata:
    languages: [Go]  # 語言標籤
    focus_area: Error Handling
```

**優點**:
- 結構一致
- 語言特定性透過 Metadata 表達
- 易於查詢特定語言的所有規則

**缺點**:
- 需要重新設計所有語言規則的 ID

---

**修正建議方案 C**: LANG 作為跨域標籤

```
不將 LANG 視為獨立 Domain，而是：

CODE Domain
├── ST - Structural Change
│   ├── CODE-ST-C-XX (通用結構約束)
│   ├── CODE-ST-C-GO-01 (Go 特定結構約束)
│   ├── CODE-ST-C-JAVA-01 (Java 特定結構約束)
│   └── ...

或

CODE Domain
├── ST - Structural Change
│   ├── CODE-ST-C-XX (通用)
│   └── LANG/ (語言子目錄)
│       ├── GO-ST-C-01
│       ├── JAVA-ST-C-01
│       └── ...
```

**優點**:
- 語言規則直接整合到 CODE Domain
- 避免重複的 Domain 定義

**缺點**:
- 增加 CODE Domain 的複雜度
- Rule ID 結構變得複雜

### 問題 2: GOV Domain 結構評估

**當前問題**:
- GOV Domain 使用 ENF、PR 作為子分類
- 這與標準的 AR、BD、CN、LG、ST、TI、TR 結構不一致

**評估問題**:
1. GOV 的 ENF、PR 是否也是一種 Behavior Constraint Category？
2. GOV 是否應該使用標準的 AR-BD-CN-LG-ST-TI-TR 結構？

**分析**:

**ENF (Enforcement)** 規則範例:
- GOV-ENF-C-01: All AI-generated code *must* comply with coding standards
- GOV-ENF-C-02: Violations *must* generate Code Validation Report

**PR (Principles)** 規則範例:
- GOV-PR-C-01: AI is a constrained executor, not an autonomous designer
- GOV-PR-C-02: All AI behavior *must* be explicitly governed

**評估**:
- ENF 接近 LG (Logging & Report) 或 BD (Boundary & Stop) 的概念
- PR 更像是高層次的治理原則，而非具體的行為限制類型

**修正建議**:

**方案 A**: GOV 對齊標準結構

```
GOV Domain
├── BD - Boundary & Stop
│   ├── GOV-BD-C-01 (原 GOV-ENF-C-01)
│   └── ...
├── LG - Logging & Report
│   ├── GOV-LG-C-01 (原 GOV-ENF-C-02)
│   └── ...
├── CN - Constraint Neutrality
│   ├── GOV-CN-C-01 (原 GOV-PR-C-02)
│   └── ...
└── ...
```

**方案 B**: GOV 保持獨立結構，但明確定義其分類邏輯

```
GOV Domain（治理專用分類）
├── ENF - Enforcement (執行機制)
│   定義：確保規則被執行的機制與流程
│
└── PR - Principles (治理原則)
    定義：高層次的 AI 治理哲學與原則
```

**建議**: 方案 B，因為 GOV 的 ENF、PR 確實有別於技術性的 AR-BD-CN 分類

---

### 問題 3: DOCS Domain 缺少 LG 類別

**當前狀態**:
- DOCS Domain 有 AR、BD、CN、ST、TI、TR
- 缺少 LG (Logging & Report) 類別

**評估**:
- CODE Domain 有完整的 LG 類別（7 條規則）
- DOCS Domain 理論上也應有日誌與報告需求

**修正建議**:

**方案 A**: 補充 DOCS-LG 規則

```
DOCS Domain
├── ...
├── LG - Logging & Report
│   ├── DOCS-LG-C-01: Documentation rationale must never be empty
│   ├── DOCS-LG-P-01: Each documentation generation must generate execution logs
│   ├── DOCS-LG-P-02: Execution logs must link to traceability IDs
│   └── ...
└── ...
```

**方案 B**: DOCS 復用 CODE 的 LG 規則

```
DOCS Domain 的 LG 行為直接引用 CODE-LG-* 規則
（透過 Application Ruleset 組合）
```

**建議**: 方案 A，因為文檔生成與程式碼生成的日誌需求可能不同

### 問題 4: Rule ID 編碼規則不一致

**當前 Rule ID 格式**:
- CODE: `{DOMAIN}-{CATEGORY}-{TYPE}-{NUMBER}` (如 CODE-AR-C-01)
- DOCS: `{DOMAIN}-{CATEGORY}-{TYPE}-{NUMBER}` (如 DOCS-AR-C-01)
- LANG: `{DOMAIN}-{LANGUAGE}-{TYPE}-{NUMBER}` (如 LANG-GO-C-01)
- GOV: `{DOMAIN}-{SUBCATEGORY}-{TYPE}-{NUMBER}` (如 GOV-ENF-C-01)

**問題**: LANG 的 ID 格式使用語言名稱，與其他 Domain 不一致

**修正建議**:

統一 Rule ID 格式為：`{DOMAIN}-{CONSTRAINT_CATEGORY}-{TYPE}-{NUMBER}`

範例：
- CODE-AR-C-01 ✓
- DOCS-ST-C-01 ✓
- LANG-ST-C-01（語言通用結構約束）
- LANG-ST-C-02（特定語言結構約束，透過 Metadata 標註語言）

### Phase 1: 定義標準的 Behavior Constraint Category

**目標**: 明確定義 AR、BD、CN、LG、ST、TI、TR 的含義與適用範圍

**產出**: `BEHAVIOR_CONSTRAINT_CATEGORY.md`

**內容**:
```markdown
# Behavior Constraint Category 定義

## AR - Artifact Isolation (製品隔離)
- 定義：確保生成的製品（程式碼、文檔等）之間的隔離與獨立性
- 適用 Domain: CODE, DOCS, LANG, GOV
- 典型規則：不得修改未聲明的製品類型

## BD - Boundary & Stop (邊界與停止)
- 定義：定義 AI 執行的邊界與停止條件
- 適用 Domain: CODE, DOCS, LANG, GOV
- 典型規則：不得修改聲明邊界之外的程式碼

## CN - Constraint Neutrality (約束中立性)
- 定義：AI 不應推斷未聲明的約束或需求
- 適用 Domain: CODE, DOCS, LANG, GOV
- 典型規則：不得推斷未聲明的邊界

## LG - Logging & Report (日誌與報告)
- 定義：執行過程的日誌記錄與報告生成
- 適用 Domain: CODE, DOCS, LANG, GOV
- 典型規則：每次執行必須生成執行記錄

## ST - Structural Change (結構變更)
- 定義：對系統結構的修改控制
- 適用 Domain: CODE, DOCS, LANG, GOV
- 典型規則：禁止未經授權的結構重構

## TI - Test Integrity (測試完整性)
- 定義：確保測試的獨立性與完整性
- 適用 Domain: CODE, DOCS
- 典型規則：測試不得修改生產代碼

## TR - Traceability (可追溯性)
- 定義：確保生成的製品可追溯到原始需求
- 適用 Domain: CODE, DOCS, LANG, GOV
- 典型規則：生成的代碼必須包含追溯 ID
```
