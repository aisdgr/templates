# DOCS Rule Catalog

This directory contains the **DOCS rule catalog**, which defines
**document-level structured constraints** for AI-assisted and automated
document generation and modification.

These rules are **scenario-agnostic**, **document-type-independent**, and
**governance-neutral by design**.

They define **what document-level actions are allowed or forbidden**,
not *why*, *when*, or *by whom* they should occur.

---

## 1. Design Principles

The DOCS rules follow the following non-negotiable principles:

1. **Document-Level Only**  
   Rules apply strictly to document artifacts and document-generation behavior.
   They do not reference source code, build processes, organizational roles,
   or governance authorities.

2. **Scenario-Free**  
   Rules do **not** encode intent such as `create`, `update`, `review`, or
   `approve`.  
   Scenarios are composed later by selecting appropriate rules
   into a ruleset.

3. **Boundary-First and Fail-Stop**  
   When required generation scope is missing, conflicting, or invalid,
   execution MUST stop immediately.

4. **Composable and Reusable**  
   Each rule is atomic and reusable across multiple rulesets.
   Rules never depend on other rules or policies.

5. **Execution Rules vs. Governance Guardrails**

   DOCS explicitly distinguishes between two semantic types of rules:

   - **Execution Rules (MUST)**  
     These define *document engineering obligations* such as completeness,
     structural validity, or content traceability.  
     Violations indicate missing or incomplete work and are typically
     remediable.

   - **Governance Guardrails (MUST NOT)**  
     These define *hard prohibitions*.  
     Any verified violation constitutes an **evidence-based governance
     trigger** and MUST result in execution stop, recording, and escalation
     by higher-layer governance systems.

   **Only violations of governance guardrails (MUST NOT) produce
   hard governance triggers**.

---

## 2. Rule ID Naming Convention

All rules in this directory follow the same identifier format:

```
DOCS-<CATEGORY>-<TYPE>-<NN>
```

Example:
- `DOCS-BD-C-01`

Where:
- **DOCS** indicates the document domain
- **CATEGORY** indicates the rule classification
- **TYPE** is `P` (Policy / MUST) or `C` (Constraint / MUST NOT)
- **NN** is a sequential number within the category and type

Rule IDs are **stable** and **never change** due to ruleset composition.

---

## 3. Rule Classification Overview

The DOCS rule catalog is organized into **six fixed categories**.
Each category represents a distinct **document engineering risk domain**.

For governance-relevant risk domains, **at least one rule in the category
MUST be a governance guardrail (MUST NOT)** to provide an explicit
evidence-based trigger.

| Category | Name                 | Risk Domain Focus                                        |
| -------- | -------------------- | -------------------------------------------------------- |
| BD       | Boundary & Stop      | Generation scope and hard stop conditions                |
| AR       | Artifact Isolation   | Cross-section and cross-artifact contamination           |
| TR       | Traceability         | Semantic source integrity and document traceability      |
| TI       | Test Integrity       | Test specification consistency and intent preservation   |
| ST       | Structural Integrity | Section structure, content completeness, and field rules |
| CN       | Inference Control    | Implicit inference and undeclared content generation     |

No rule may exist outside these categories.

## 4. Rule List and Descriptions

### BD — Boundary & Stop

Defines **non-negotiable generation guardrails**.  
Ensures generation is explicitly scoped and human accountability is preserved.

#### **DOCS-BD-P-01**
- category: execution
- description: Generation MUST be explicitly scoped to requested sections.

#### **DOCS-BD-P-02**
- category: execution
- description: Human accountability and oversight MUST be maintained.

#### **DOCS-BD-C-01**
- category: governance
- description: Document immutability MUST be enforced after approval.

#### **DOCS-BD-C-02**
- category: governance
- description: Policy violation MUST result in execution termination.

---

### AR — Artifact Isolation

Prevents unintended content generation outside declared regions
or across document artifact boundaries.

#### **DOCS-AR-C-01**
- category: execution
- description: AI MUST generate content only within declared placeholders in the document template.

#### **DOCS-AR-C-02**
- category: governance
- description: Content that spans multiple sections MUST NOT be generated.

#### **DOCS-AR-C-03**
- category: governance
- description: Appendix content MUST NOT be generated by default.

#### **DOCS-AR-C-04**
- category: execution
- description: AI MUST produce a structurally valid document artifact.

---

### TR — Traceability

Ensures document content is anchored to recognized and declared semantic sources.

#### **DOCS-TR-P-01**
- category: execution
- description: Recognized semantic sources MUST be used.

---

### TI — Test Integrity

Ensures test specifications are not altered or reinterpreted during document generation.

#### **DOCS-TI-P-01**
- category: execution
- description: Test specifications MUST follow item policy.

---

---

## 5. Notes on Rulesets and Future Extensions

- **Rulesets** only select and compose rules.
  They do not define new semantics.

- Governance severity, risk classification, and escalation logic
  are intentionally **out of scope** for DOCS.

- Future domains will use separate namespaces, for example:
  - `LANG-<LANG>-*`
  - `GOV-<CATEGORY>-*`

---

## 6. Summary

The DOCS rule catalog defines the **minimum enforceable contract**
for safe, traceable, and structurally valid document generation.

If a constraint cannot be evaluated at the document-content level,
it does not belong here.
